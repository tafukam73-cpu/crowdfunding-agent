## 0. ベンチマークが固まった原因（調査結果）

- 旧ベンチ（`_bench_live.py`）は **20案件を1プロセスで逐次実行し、1案件あたりの時間上限が無かった**。1案件で最大150回（before50+after100）の実 httpx 取得を行う。
- `httpx.Client(timeout=6.0)` の timeout は **操作単位**（connect/read/write 各6秒）で総実行時間の上限ではない。19件目 **Knog** が遅延応答を返し続け read が延々継続 → 1案件が事実上ハング → 全体停止。
- 副次的に、**実サイトの応答が 1.5〜3.0秒/ページと遅い**ことが判明（旧ベンチは1案件4〜6分・約1時間走った末に固まっていた）。
- 対策として **1案件=1 subprocess・60秒強制kill・全体30分上限・1件ごとJSON保存・再開可**のベンチ機構を用意して計測（ベンチ用スクリプトは一時ファイルのためコミットせず、計測後に削除）。

## 2. Contact ページ到達率の改善（`a5e628e` の一部）

### 背景 / 原因
- 難読化改善後もベンチのメール発見率が動かなかった。原因は **巡回がメールの載るページ（Contact・locale・Shopify policy）へ到達していない**こと（例：Nanoleaf は `/en-US/contact-us/`、Fellow/Gravity は素メールが Contact ページにあるが未クロール）。
- 旧クローラは単純 FIFO（優先パスを順に enqueue、発見リンクは末尾追加）で、限られた巡回予算内で Contact に届かないことがあった。

### 対応内容（`recursive_crawl_service.py`）
- **優先度付きキュー（heapq）** に再設計：`_url_tier()` で tier0=Contact → tier1=Support/Help → tier2=About/会社/流通 → tier3=汎用。Contact を必ず先に巡回。
- **locale 付き Contact 対応**：root のリンクから `/en-US/` 等を検出し locale Contact を seed ＋英語 locale フォールバック（`/en-US/contact-us` 等）。
- **Shopify/WordPress 系パス追加**：`/policies/contact-information`・`/pages/contact(-us)`・`/pages/about`・`/imprint` 等。
- **robots/sitemap 由来 URL の優先語** に contact/support/help/company/press/distribution/partner/wholesale/retailer/dealer。
- **早期打ち切り**：メール/フォーム/LinkedIn のいずれか確保後は tier3（商品・記事等の汎用）を打ち切り（要件 6・7）。
- **無限巡回防止**：`?page=`・`/page/N`・日付アーカイブ・`/tag/`・`/category/` を除外。

### 効果（数値・同一20案件、両run ok成立16件のマッチ比較）
| 指標 | 改善前 | 改善後 |
|---|---|---|
| メール発見率 | 10/16 (62%) | **13/16 (81%)** |
| フォーム発見率 | 13/16 (81%) | 14/16 (88%) |
| 営業可能チャネル発見率 | 14/16 (88%) | **15/16 (94%)** |
- メール新規発見：**Nanoleaf・Fellow・Gravity Blanket**（純粋な到達率効果）。

## 3. 1URL ハードタイムアウト ＋ クロール全体の時間予算（`26d1b09`）

### 背景 / 原因
- Flow Hive / Nomad（1.5〜3秒/ページの低速）・Nura（robots.txt が約60秒ハング）で探索が止まる/結果を失う。
- Nura は httpx の read timeout(5s) を貫通するハング（トリクル応答・多段リダイレクト）で、粒度別 timeout では止められなかった。

### 対応内容（`recursive_crawl_service.py` / `config.py`）
- **1URL ハードタイムアウト**：各 fetch を専用 **daemon スレッド**で実行し `join(per_url_timeout)` で期限。期限超過URLは破棄してクロール継続（URLごと専用スレッドでワーカー枯渇なし、daemon でプロセス終了を妨げない）。robots/sitemap/巡回の全 fetch に適用。
- **クロール全体の時間予算**：超過時に **発見済み結果（メール/フォーム/SNS/チャネル）を保持したまま**巡回・PDF解析を打ち切り、`TIMEOUT` を失敗理由に記録。
- 設定：`recursive_crawl_url_timeout=10.0` / `recursive_crawl_max_seconds=45.0`（.env 上書き可）。

### 効果（実地確認）
| 案件 | 従来 | 改善後 |
|---|---|---|
| Flow Hive | ハング→結果0 | 約55s / `info@honeyflow.com` 回収 / form / ch12 |
| Nomad | ハング→結果0 | 約42s / form / ch74（公開メール無・フォーム窓口） |
| Nura | robots.txt で約60秒ハング | 約43s / CRAWL_BLOCKED（Cloudflare・元々メール無）で境界内返却 |
- 3案件とも **約55秒以内に必ず結果を返す**ようになった（無限ハング解消）。

## 1. Contact Intelligence の完全ジョブ化（`e837aa6`）

- 「読み込み失敗：タイムアウト：12秒以内に応答がありませんでした」は、重いPOST自体ではなく**同一画面が並行して投げる軽量GET `/projects/{id}` (`fetchProject`) がタイムアウト**していた（フロント `apiFetch` の `DEFAULT_TIMEOUT_MS=12000`・AbortController）。
- 真因：**単一 uvicorn ワーカー**上で自動抽出/AI/Document Reader/v2 が**同期POSTのリクエスト内で実行**され、60秒以上ワーカーを占有 → 並行GETがタイムアウト。`web_research`/`search_agent` は既にジョブ化済みだったが、残り4つが同期のまま取り残されていた（前回の httpx-first fallback は Playwright 起動を減らしただけで同期実行という設計は残っていた）。

### 対応
- `CIJobType` に `contact_discovery` / `contact_discovery_v2` / `ai_research` を追加（`job_type` は `String(40)` のため **DBマイグレーション不要**）。`contact_intelligence_service` に各ランナー＋ `_SINGLE_PHASES` を追加。
- フロント（`ContactDiscoveryPanel`）の `onRun`/`onRunAi`/`onRunDoc`/`onRunV2` を同期 `runResearch` → 非同期 `runAsJob`＋`pollJob` へ統一。専用ポーリング ref を追加し、リロード時の進行中ジョブ購読も全 job_type に拡張。
- 変更：`backend/app/models/contact_intelligence_job.py` / `contact_intelligence_service.py` / `frontend/lib/api.ts` / `frontend/components/ContactDiscoveryPanel.tsx`。

### 効果（実API検証）
- POST → **job_id を 0.02s で返却**（queued）。実行中の GET `/projects/{id}` は最悪でも 4.8s（CPUバースト時）で **12秒未満**、ポーリングGETは ~7ms。24hキャッシュ再利用も 0.009s。
- テスト：`test_contact_intelligence_jobs` 19 passed／回帰 green。**12秒タイムアウトは再現せず。**
- 教訓は memory [[ci-heavy-work-must-be-jobs]] に記録（重い探索は同期POST禁止）。

## 2. 営業AIコパイロット（`0c5bcc9` / `f658a8f`）

### 目的 / 設計
- 案件・企業リサーチ・Contact Intelligence・CRM・営業状況・返信/フォロー状況を横断し、案件ごとに**1つの判断＋理由＋次の一手＋アクション**を提示（ルールベース・Claude非依存）。
- 既存 `executive_summary_service`（スコア/日本相性/連絡先/担当者/リスク）を**再利用**し、企業リサーチ済み/メール生成済み/公式サイト確認済み/最終営業日数を加えて判断。`build_card()` の `summary` を独立dictにし、後で Claude 要約を差し込める構造。

### 判断ロジック（先勝ち）

### 検証

## 3. Wadiz（韓国）・Zeczec（台湾）収集追加（`8c8cfbf`）

### 実サイト調査で判明したこと
- **Wadiz**：SPA本体・`public-api` は Akamai で 403。しかしトップが叩く公開 JSON API **`platform.wadiz.kr/main2/api/v1/pc/main/funding`** を Playwright のネットワーク傍受で発見。ブラウザ相当ヘッダー（Origin/Referer）付き **httpx で 200**（Playwright不要・軽量）。
- **Zeczec**：`/` `/explore` は 403 だが **`/categories` の server-render HTML は 200**。カード `a[data-content-type="project"]` からタイトル/URL/画像/NT$調達額/達成率/支援者数/残日数を抽出（詳細ページは 403 のため使わない）。

### 対応
- 新規 `backend/app/scrapers/wadiz.py`（JSON API）・`zeczec.py`（HTML）。`ProjectCreate` へ正規化 → 既存 collector が `projects` へ upsert（source_url 重複判定）。達成率(rate) から目標額を逆算。国/ステータス/達成率は `[Wadiz]`/`[Zeczec]` マーカー付きメモに記録。取得失敗は `blocked/empty_result/network/structure/parse_error` に分類して送出（0件握りつぶし禁止）。
- `SourceSite.zeczec` 追加、`SALES_TARGET_SITES`/`OVERSEAS_SITES`/`DASHBOARD_SITES`/`registry` に配線。フロント `SITE_LABELS`/`SITE_COLORS`/`SALES_TARGET_SITES` に反映。Sales Copilot は `SALES_TARGET_SITES` 経由で自動対象化。

### 検証（実API）
- **Wadiz 8件 / Zeczec 8件** を実取得 → `projects` に created。Zeczec 再取得で created=0/updated=8（dedup確認）。
- 一覧APIに表示（`site=wadiz` total 9 / `site=zeczec` total 8）。Sales Copilot scanned **91→111**。Wadiz案件(実campaign URL)で Contact Intelligence ジョブが起動→完了。
- `test_wadiz_zeczec` **35 passed**（正規化・URL絶対化・達成率→目標額逆算・ページング/limit・dedup・エラー分類）。回帰 green・`tsc` green。
